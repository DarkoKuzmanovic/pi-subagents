## Goal

Add a first-class in-TUI lane editor to `/subagents` so users can view, add, edit, and remove `subagents.modelLanes` entries (model + thinking per role/lane) and have those edits written back to `~/.pi/agent/settings.json` — without hand-editing JSON. The TUI becomes a second, equivalent editor over the same lane shape the JSON control plane already owns, with no change to lane dispatch runtime semantics.

## Scope in

- A lane store layer with safe read-modify-write semantics over `subagents.modelLanes`: create lane, update a lane's `model`/`thinking`, and remove a lane, each preserving all other settings fields, validating model/thinking, and writing atomically (mirroring `seedModelLanesIfMissing`'s preserve-existing discipline).
- A lane-editor TUI surface reachable from `/subagents` that lists each role's lanes with model + thinking, and supports add / edit / remove with model and thinking pickers.
- Resolve the standing UX open question for this surface: whether unsupported thinking levels are shown disabled or filtered, based on the model's `thinkingLevelMap`.
- A compact `/subagents` help hint for the lane-editor entry point / keybinding (polish-backlog item).
- Coexistence with the existing `/subagents` model hub and `/subagents config|json|edit` JSON shortcut: both editors operate on the same shape and stay round-trip consistent.
- Docs + tests for the lane store, the entry point, and TUI rendering where the harness allows.

## Scope out

- Editing **project-scope** lanes from the TUI. M2 edits **user-scope** settings only (matching `/subagents config`); project-scope lanes, if present, are displayed read-only. Project-scope editing is a later candidate.
- Changing lane **dispatch runtime** semantics or precedence (owned by M1; M2 is editor-only).
- Automatic task-difficulty classification or auto-routing by task content (still explicitly out, per M1 decision).
- New lane fields beyond `model` + `thinking` (e.g. per-lane tools/skills).
- Provider bakeoff execution or any model-quality conclusions.
- Removing or re-enabling compatibility agent files, or changing the six-role roster.
- Changing Pi core model or thinking semantics.
- Reworking unrelated dirty working-tree files.

## Acceptance criteria

- From `/subagents`, the user can open a lane editor that lists each configured role and its lanes with the lane's `model` and `thinking` values.
- The user can **add** a lane, **edit** a lane's `model` and `thinking`, and **remove** a lane; each change persists to `~/.pi/agent/settings.json`.
- Writes are **round-trip safe**: all unrelated settings fields are preserved byte-for-intent (same atomic write + trailing-newline discipline as `seedModelLanesIfMissing`), and re-reading via `readModelLanesFromSettingsFile` returns the edited lanes without error.
- Thinking validation rejects values outside `THINKING_LEVELS`; `off` is treated as an intentional level, not "missing".
- The editor never duplicates or corrupts `:thinking` model-suffix state (watch-list risk): the lane `model` field and the `thinking` field stay distinct exactly as the lane shape defines them.
- Invalid existing `subagents` / `modelLanes` shapes produce a clear error and **do not** silently overwrite user settings.
- The existing `/subagents` model hub and `/subagents config|json|edit` paths continue to work unchanged; lane edits made in either editor are visible to the other.
- Tests cover the lane store (create / edit / remove / preserve-other-fields / validate / invalid-shape error) and the slash entry point; TUI render coverage is added where the existing widget/hub test harness allows.
- Relevant targeted tests pass; if broad `npm run typecheck` still reports pre-existing project errors, the executor records exact evidence and verifies M2-specific files independently.

## Phase boundary health

M2 leaves the extension operational and coherent: the lane editor is **additive** over the same `subagents.modelLanes` shape the JSON control plane already owns, and changes nothing about lane dispatch. If the TUI editor were removed, `/subagents config` JSON editing and lane dispatch would still work identically. There is no half-applied migration, no dangling integration, and CI is expected green. Later milestones (project-scope lane editing, richer lane fields) can extend this without invalidating M2.

## Constraints / invariants

- Planning artifacts live under `.pi/pmti/`; implementation belongs to PMTI task execution (`pmti-implementation`).
- Settings writes must preserve unrelated fields, be atomic, `mkdir -p` the parent, and end with a trailing newline — matching `src/slash/subagents-config.ts` (`seedModelLanesIfMissing`).
- Single `:thinking` normalization boundary is preserved; the lane editor must not introduce a competing suffix mechanism or corrupt existing suffix state (watch-list: "TUI model suffix coupling").
- Runtime dependencies remain Node built-ins, `@earendil-works/*`, and `typebox`.
- ESM TypeScript conventions: `.js`/`.ts` import specifiers per project style, no `any`, no new non-null assertions, type-only imports where appropriate.
- Node built-in test runner only; reuse existing support shims and render-test patterns (`test/integration/render-*.test.ts`, hub/widget tests).
- Existing dirty working-tree files are live state; executors classify them before editing and preserve unrelated changes.
- User-scope settings only for editing in M2; project-scope lanes are read-only in the TUI.
