# WB-03: Multi-file integration change

## Goal

Carry one approved behavior through 3-5 files without losing existing conventions. The worker should trace the flow, update all required call sites, and keep the boundary ownership clear.

## Starting point

Parent provides:

- The approved behavior change.
- The expected flow: input → entry point → core logic → output.
- The likely files or symbols, if known.
- The command that exercises the integrated path.

Good examples: add metadata to a run result, thread a new option through foreground/background execution, or include a new field in both status rendering and serialized output.

## Allowed scope

Allowed:

- Edit the named flow and directly adjacent types/tests.
- Add compatibility handling if older persisted data may not have the new field.
- Update user-facing docs for the changed behavior.

Forbidden:

- Forking the flow into a parallel implementation.
- Duplicating helpers instead of using existing shared utilities.
- Touching unrelated execution modes.

## Verification

Required checks:

```bash
npm run test:unit -- <target-unit-tests>
npm run test:integration -- <target-integration-tests>
npm run typecheck
```

The worker must list the exact flow it traced in the final response.

## Scoring notes

This task primarily measures integration reliability. Score down for partial call-site updates, stale types, missing backwards compatibility, or fixes that only work on the narrow happy path.
